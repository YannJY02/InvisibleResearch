## 1. “用模型分析”在这里指什么

导师在 **07:44** 明确说的是机器学习预测，**17:50** 再次说明要找出哪些列能够预测期刊是否被 Scopus 收录。数据获取端是 **OpenAlex Source API**；06:59 的“open Ai”是转录中的表述，不改变上下文中的接口身份。研究者在 15:39 用了 LLM 一词，但对话没有建立调用大语言模型分析全部 JSON 的方案。

本轮读回的[导师上游 #5 评论](https://github.com/invisibleinfo/invisible-research/issues/5#issuecomment-5553748839)（更新于 2026-09-29）同样明确：按 ISSN 匹配 Scopus，再用 Boruta 和／或 SHAP 分析期刊特征与 Scopus visibility（0/1）。这进一步支持下述理解；二元形式本身还不能决定哪些记录可以可靠编码为 0。

| 要素 | 当前能明确的含义 | 仍需决定的内容 |
|---|---|---|
| 分析对象 | 一行是一种期刊，以 OpenAlex Source ID 识别 | 进入模型的年份、期刊范围和排除规则 |
| 预测结果 `y` | 期刊是否被 Scopus 收录 | 名录出现、当前 Active、曾经收录或未来首次收录，不能混用 |
| 输入特征 `X` | 国家、学科／主题、规模、引用、OA／APC、论文语言等 | 最终列、缺失处理、主题表示及时间窗 |
| 模型工作 | 根据已有可靠标签学习特征与收录的关系，再验证表现 | 具体学习器、基准、数据切分和性能标准 |
| 特征解释 | 比较哪些特征帮助模型预测 | 解释不能单凭重要性转为因果或歧视结论 |

[既有 7 月方法记录](../../meeting-reports/2026-07-28-ojs-enrichment-next-steps.md)和 INVIS-10 保留了简单模型与 Boruta／SHAP 的方向。需要分清作用：分类模型作预测，Boruta／[BorutaShap](https://github.com/Ekeany/Boruta-Shap)用于筛选特征，[SHAP](https://shap.readthedocs.io/en/latest/)解释已训练模型的输出。随机森林、XGBoost 等可以作为候选学习器；昨天没有确定使用哪一种，提到 Boruta／SHAP 也不等于整个方法已经定稿。

因此，目前讨论的是**期刊层面的监督学习分类**。若后来另设 LLM 阅读、文本编码或语义分析任务，输入形式和评价方式需另行定义，不能由 JSON 后缀推导出那条路线。

## 3. 哪种格式适合模型分析

**2026-09-30 执行选择：**用户接受保留原始 JSON 的加工路径，并明确本轮转成 CSV、
暂不导入 PostgreSQL，优先处理速度。按此启动[完整 Source JSON 与合并 CSV](source-api-csv.md)。
下表保留会后格式比较，Parquet 不再是本轮交付要求。

需要同时回答两个问题：信息怎样完整保存，以及模型最终学哪些变量。文件格式决定读写与类型保存；**固定、可比较的列定义和特征编码才决定模型能否使用这些数据。**

| 形式 | 合适的用途 | 本项目的建议与限制 |
|---|---|---|
| 一刊一个原始 JSON | 保存完整响应，保留嵌套字段和可追溯原件 | 执行昨日约定；不为某个模型提前删字段 |
| JSONL，一行一个 Source 对象 | 可选的批量顺序读取或交换副本 | 可从原 JSON 另行生成；不替换原件，不表示已完成特征编码 |
| 有类型的明细表，优先 Parquet | 保存期刊、主题、年度、语言等中间数据 | 数值、布尔、空值及嵌套类型更易保留，适合后续反复读取 |
| 一刊一行的分析特征表，优先 Parquet | 保存固定列含义的标量特征与结果标签 | 进入 R／Python 后还需按学习器处理类别、缺失和列模式 |
| CSV | 便于人工检查及通用交换 | 保留既有 CSV 交付，可导出扁平特征表；嵌套内容需额外序列化与解析，类型及空值需伴随说明 |

Parquet 是面向分析的列式格式，可压缩并按列读取；Arrow 的 [R 读写说明](https://arrow.apache.org/docs/r/articles/read_write.html)展示了 data frame 与 Parquet 的往返，[嵌套数据说明](https://arrow.apache.org/blog/2022/10/08/arrow-parquet-encoding-part-2/)说明了变长列表和结构体的保存。**能保存 list 不意味着学习器能直接分析 list。** 例如 [XGBoost 的类别说明](https://xgboost.readthedocs.io/en/stable/tutorials/categorical.html)要求正确的数值／类别类型及一致编码；每格放任意 JSON 字符串仍需先处理。

建议沿用“**原始 JSON → 各类明细／汇总 → 固定特征表 → 训练与验证**”的顺序。Parquet 是分析数据的保存建议；CSV 是查看与交换形式，两者可以由同一份确定列模式的数据产生，不应维护两套独立计算逻辑。

## 4. 怎样合并，同时保持一刊一行

以下是根据现有数据约定提出的实施规则，昨天并未逐项确定 SQL 或输出列。

| 数据关系 | 用什么连接 | 连接前后怎样保持含义 |
|---|---|---|
| 期刊基表 ↔ Source JSON | OpenAlex Source ID | 保留原清单的每个 ID；记录请求失败、返回身份变化与获取时间 |
| 期刊 ↔ 论文 | 主要发表载体对应的 Source ID；本库为 `works.primary_source_id` | 先定义时间窗与 work 类型，对 work ID 去重；不把所有存放位置都当作发表期刊 |
| 期刊 ↔ topic | 按 `source_id` 连接；主题明细粒度为 `source_id` + `topic_id` | 明细可以多行；同一论文同一主题不重复计数；模型汇总按期刊输出一行 |
| 期刊 ↔ 年度 | 按 `source_id` 连接；年度明细粒度为 `source_id` + `year` | 固定每刊每年唯一及年度口径，再选择年份列或窗口统计 |
| 期刊 ↔ 语言 | 按 `source_id` 连接；语言明细粒度为 `source_id` + `language` | 保存计数、比例和分母；按语言汇总后转成固定特征 |
| OpenAlex ↔ Scopus | 校验后的 print／electronic／linking ISSN 交集 | Source ID 不能代替跨库 ISSN；保存全部候选，歧义交给规则裁决 |

主题、年度、语言要**分别汇总，再与期刊基表连接**。假设某刊有 10 条主题和 5 条年度记录，先把两张明细直接连接会生成 50 行；若此时求和，原有数值会被重复累计。新增语言明细还会继续放大。保留子表，或各自生成一刊一行的汇总后再合并，才能避免这种错误。

期刊基表使用左连接保留全部输入期刊。每个一刊一行汇总先检查 Source ID 唯一性，合并后核对 ID 集合、行数和连接覆盖。多个 ISSN 对应同一 Scopus Source 的证据可合并；对应多个不同候选则保留歧义，不能任取第一条。旧 CSV 保留的重复子记录也不能直接相加，见[原交付记录](journal-export.md)与[输入约定](input-contract.md)。

## 5. 主题数量不同，怎样变成可比较的特征

### 5.1 先保留身份、数量和层级

主题明细至少保留 `source_id`、`topic_id`、名称、subfield／field／domain 的 ID 与名称、来源时间和列表类型。`topics` 条目保留 `count`，`topic_share` 条目保留 `value`；字段不在对应条目中时保持未提供，不能互填。以 **topic ID** 识别同一主题，名称供阅读；不同列表或不同字典版本不能只凭名称合并。

不能把不同刊的 `topic1` 都当作同一个主题。它只表示“这本刊排名第一的主题”，A 刊可能是医学，B 刊可能是传播学。若保留这种排名变量，应明确其身份和编码；更可比较的表示是“同一主题／field／domain 在各刊各占多少”，每一列对所有期刊有相同含义。

### 5.2 完整响应有覆盖边界

2026-09-30 核对了[官方 Source 属性说明](https://help.openalex.org/data/sources/attributes/)及现有[字段补全简报](field-recovery.md)引用的[固定公开 Source 聚合代码](https://github.com/ourresearch/openalex-walden/blob/7021748a6946c262484437b356f355d2b9e1a494/notebooks/sources/CreateSourcesApi.ipynb?plain=1)。该版本对 `topics` 按 count 排序、对 `topic_share` 按 value 排序，**分别取前 25 个**；两份列表不必有相同条目。9 月 29 日保存的 Journal of Communication 样例两份列表也各有 25 条。这是固定代码和一个已保存响应的观察，不是对所有期刊未来响应形状的保证。

所以“完整 JSON”指**保存完整 API 响应**，不能写成“已经获得这本刊全部论文的全部主题”。只在返回列表中没看见某主题，不能断言本刊该主题的论文数为 0；仅把返回主题按 domain 相加，也不能当作完整、互斥的学科分布。

### 5.3 三种数量不能混用

| 指标 | 分子／分母及含义 | 注意事项 |
|---|---|---|
| `topics.count` | 本刊属于该主题的独立 work 数 | 一篇 work 可有多个主题，跨主题相加可超过期刊论文数 |
| 拟计算的刊内主题比例 | 同一窗口内本刊该主题 work 数 ÷ 本刊纳入的 work 总数 | 是本刊内容构成；多主题口径下各比例之和可超过 100% |
| API `topic_share.value` | 该刊该主题 work 数 ÷ 全库有 primary source 的该主题 work 数 | 是期刊对该主题的贡献份额，不是该主题占本刊的比例 |

分母必须来自相同作品范围和版本。不能用只统计主主题的 `topics.works_count` 代替全部主题关系的全库分母，也不能把 API 的跨期计数除以另一个窗口的期刊论文数。公式与全部主题／主主题的区别见[字段补全简报](field-recovery.md)；[官方 aboutness 说明](https://help.openalex.org/data/aboutness/)提供了 topic → subfield → field → domain 的分类层级。

### 5.4 建议比较的表示方案

| 方案 | 能回答什么 | 使用条件与取舍 |
|---|---|---|
| 最大 topic／其 field／domain | 期刊主要围绕哪类内容 | 接近导师提出的简洁方案；保留来源、并列规则和未知状态，不能代表全部内容 |
| 固定 field／domain 的比例列 | 各刊学科构成怎样不同 | 建议作为第一轮较容易解释的候选；准确完整比例需从对应论文集合汇总 |
| 固定 topic ID 的出现／数量／比例列 | 更细的主题与收录怎样关联 | 可用稀疏表示；主题多，需检查稀有类别、规模效应及特征选择稳定性 |
| 前二／前三主题及其信息 | 兼顾主要与次要内容 | top-k 是候选超参数；列含义和类别编码需明确，不能只拼接名称 |

**建议第一轮先比较主要 field／domain 等简洁特征，再决定是否增加细粒度主题。** 若需要总和为 100% 的学科比例，可从每篇论文的主主题映射到 field／domain，保证一篇论文只分配一次，并单列未分类比例。这是研究表示的建议；它不同于复现 API 使用全部主题的计数，不能叫作 API 原字段。若使用全部主题，则须说明多重归属；同一论文同一 domain 要去重，跨 domain 比例不一定互斥。

只有已取得完整关系、且覆盖规则允许确认缺席时，相应主题列才可填真实 0。抓取失败、无分类、缺少字段或 top-25 列表未出现都要与 0 分开。类别词表、稀有类别合并及特征筛选在训练数据内确定，再原样应用于验证数据。

## 6. 年度数据、语言和版本还要注意什么

**年度。** 不同期刊的年份跨度不同，按 `year` 对齐，不按数组位置连接。先固定共同窗口，再生成如窗口发文量、OA 比例、年度变化等候选列；缺年是否能解释成 0 要看源覆盖。当前公开计算代码中的年度引用，是该年发表作品截至数据版本的累计被引，不等于期刊在该年收到的引用。两年平均被引的窗口也不能仅凭字段名猜测，沿用[字段补全简报](field-recovery.md)的版本与公式说明。旧年度子表存在重复及数值异常，API 新值与旧库值保留来源，不能悄悄覆盖或相加。

**语言。** 导师关心发表论文的语言；英语摘要不能证明正文为英语。会议讨论了 Works API 样本和 BigQuery 汇总两条路线。BigQuery 全量应理解为**所选数据库中符合规则的全部可用论文**，不自动等于期刊真实全部发表量。优先复用认可的 BigQuery 路线，同时记录语言字段的覆盖和来源，不声称已核验全部正文。

语言汇总建议保留论文总数 `n_works`、语言已知数 `n_language_known`、未知数、各语言计数。以全部纳入论文为分母的英语比例与以语言已知论文为分母的英语比例含义不同，应命名并注明；后者分母为 0 时是未知。单值语言码可直接计数；若实际来源出现多语言值，需要另定全计数或分数计数，不能复制行后把分母也增加。样本比例要保留样本量与抽样方法，不能称为全刊比例。“英语刊／多语言刊”阈值昨天没有定。

**缺失。** 原始 `null`、空字符串、空列表、字段未返回、抓取失败、真实 0、未知 Scopus 标签分别保留。分析时怎样处理缺失取决于字段含义和学习器；不能在下载阶段统一填 0。任何填补、编码和筛选只在训练部分拟合，沿用[既有模型准备建议](premeeting-report.md#6-现在能否开始-borutashap)。

**版本。** 当前基表来自 January 2026 BigQuery；新 API 是获取时状态；已用 Scopus 名录是 August 2026 版。用 ID 连接只解决身份，不会把它们变成同日快照。需决定是使用近似同期数据做横截面分类并说明时间差，还是使用历史特征预测未来收录并另取时间一致的结果。引用量、发文规模等可能受收录影响，横截面关联不能解释为收录原因。

**标签与泄漏。** Scopus 未匹配、无有效 ISSN、多候选、Inactive 和未知状态不是同一种负例。实际预测标签须由 INVIS-9 的名录范围和规则产生。完整 JSON 可以保留所有字段，但模型列要排除直接给出目标收录状态的字段、目标生成字段以及纯标识符；其他名单变量需审查与结果的来源依赖。OpenAlex `is_core` 是 CWTS Core 标记，不是 Scopus 或 WoS 真值。DOAJ 等有独立研究含义的属性是否纳入，应按问题和来源评估，不能一概当作结果或一概删除。
